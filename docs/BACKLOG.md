# 設計原則

（2026-08-06 與使用者討論「去中心化帳本社交網路」的產出。記在這裡是因為它們會否決掉
一整類看起來很合理的功能，而否決的理由過幾個月就會忘掉。
原則一是後來補的——它比其餘幾條更根本，也把原本懸著的那個資料模型問題關掉了。）

## 一、帳不是債

> **債是透支未來，帳是來時路。**

- **債指向前方。** 它是對未來的你的請求權，會產生義務；義務產生槓桿；
  而槓桿正是脅迫住的地方（見原則二）。
- **帳指向後方。** 它對任何人都沒有請求權，它只能提供資訊。

帳的用途是**內省**——回頭看那條路、反思，甚至挖出自己沒發現的人生漏洞。
**它的讀者是寫的人。**

### 這條直接鎖死一個決定：不做分帳

只標 `paidBy`、不算應收應付，**不是範圍取捨，是憲法**。
加上應收／應付的那一刻，帳就變成債。這條是讓這個東西維持是帳本、不變成債本的防線。

### 帳是鏡子，不是信號

這是比「同步帳本不能當信用憑證」（原則二）**更根本**的說法：
帳根本不是人際證明的工具。要求它向第三方證明什麼是**類別錯誤**——像要求鏡子出具證明。

由此可以把兩樣長得一模一樣的東西分開：

| | 是什麼 | 讀者 |
|---|---|---|
| 自己的帳 | **證據** | 寫的人（沒有觀眾） |
| 別人給你看的帳 | **表態**——一個揭露的動作 | 被展示的那個人 |

同一個 JSON、同一套欄位，但不是同一種東西。表態可能真誠可能不真誠，
而**帳的內容對判定它真不真誠毫無幫助**——真誠與否在關係裡，不在那些列裡。
把帳當憑證之所以會失敗，就是把表態誤讀成了證據。

### 對自己誠實靠的是算術，不是意志

「對自己誠實」不是自動的：帳是同一個會自欺的自己填的，每一筆都能被合理化
（那攤算「餐飲」、那次算「必要」）。

它有效的機制其實很窄——**算術不談判。**
你可以替每一筆找到理由，但月底那個總和不接受理由；逐筆的自欺會在加總時露餡。
這正是為什麼「記帳」有效而「回想這個月花了多少」無效：
**帳的力量不在每一行誠實，而在總和不肯配合。**

⇒ 任何會讓總和失真的功能都要非常小心（估算、四捨五入、把某類支出排除在統計外、
「隱藏這筆」）。它們看起來是便利，實際是在拆掉唯一有效的那個機制。

### 推論：價值在「你沒問的模式」，不在「你問的總數」

- 你問「這個月花多少」它才回答 ＝ **查詢工具**
- 它主動說「你在超商的花費比去年同期多兩倍」 ＝ **挖掘**

按這個標準看既有功能：月結摘要卡（變動最大的分類、本月最大一筆）是對的方向——
**你沒問，它就講**。常用備註籤條是另一回事，它讓輸入變快、不讓你看得更多。
兩種都需要，但只有前一種在做「來時路」這件事。

## 二、圈層：分享的是「用途」，不是「人」

錢在華人家庭裡是**同心圓**流動的，每一圈有不同的規則：

| 圈 | 共享什麼 |
|---|---|
| 個人帳 | 只有我 |
| 家庭帳 | 我和配偶共同的（房租、菜錢、小孩） |
| 家族帳 | **只有那件共同的事**：長輩的看護費分攤、過年紅包、家族旅遊 |

現有的記帳軟體只假設「一個人」或「一間公司」，沒有人做這個結構。這是真的機會。

**但「同步帳本＝值得信任的人」這個推論是錯的，不要往那個方向做。** 三個理由：

1. **因果反了。** 不是同步證明了他誠實，是因為你已經信任他才願意同步。同步是信任的
   **結果**，不是**證據**。
2. **帳本是自己填的，沒有對抗性驗證。** 想騙你的人不必偽造帳本，他只要不記那一筆。
   而且更糟——**一本開放給你看的帳本，會把謊言洗成證據**：「我的帳你都看得到啊」這句話，
   在帳本剛好漏掉關鍵那筆的時候，說服力比沒有帳本更強。
3. **騙子的帳本會是最漂亮的。** 一個容易偽造又值得擁有的憑證，一定會被偽造。
   「有乾淨的共享帳本」一旦變成信用憑證，它就不再是信號了。

### 最要緊的一條：不要製造脅迫

如果「同步帳本」變成家族內的信任常態，那**拒絕同步就等於指控**。想想這幾個人：

- 正在偷偷存錢準備離開家暴配偶的人
- 不想讓父母看到自己消費的成年子女
- 有賭債的人——他不會因此變誠實，只會藏得更深
- 被子女以「帳給我看」當作照顧前提的長輩

**家庭正是金錢脅迫最常發生的地方。** 現在這個 app 之所以乾淨，是因為它是
**兩個已經選擇彼此的成年人**；往家族擴，同意的性質就變了——你不能選擇你的姻親。

⇒ **加入一個圈，加入的是一件共同的事，不是在證明自己的人格。**
任何會讓「不加入」顯得可疑的設計，一律不做。

## 三、外圈是繞著內圈長出來的環，不是內圈的放大版

**不要把雙人帳本一般化成 N 人帳本。** 雙人帳本是圓心，外圈是環。

這條不只是修辭，它直接推出下面兩個技術決定（`ledgerId` 不可變、分類保持全域），
也解釋了為什麼「權限模型」不該是這個 app 的重心。

## 四、時間性：留住，但不要提醒

帳本是極少數會為**平凡的一天**留下痕跡的東西。照片是策展過的——你拍的是當下就知道
值得拍的；沒有人會拍禮拜二游泳池的收據。但 `2026-08-02 八里溫水游泳池 $110` 就在那裡，
因為記帳的時候根本沒在想紀念。而最先消失、也最痛的，恰恰是平凡的那些。

一個圈總有一天會不再更新——人走了，或只是不再有交集。人容易把**回頭**和**回憶**搞混：
以為只要回去找，他們都還在。回頭是把過去當成一個還能走回去的地方；回憶是你把它背在身上，
而那個地方已經沒有了。

軟體給不了回頭。它能做的是更窄但更老實的一件事：**記憶會自己改寫，記錄不會。**
它比記憶薄得多（一行帳裝不下那個下午），但它能證明那個下午確實發生過，在哪一天，
而且你們在一起。有時候要的不是內容，是那個錨。

由此推出三條硬規則：

1. **永遠不要清。** core 有一支 `purgeableTombstones`——對「清理」要極度保守。
   省下的那點空間換不了那個。
2. **匯出的 JSON 才是真正的作品。** 不是 app，不是同步——是那份能在沒有柴米帳、
   沒有網路、沒有作者的世界裡打開的檔案。（這也是「匯出走分享面板」被排在最優先的
   更深理由，不只是資料安全。）
3. **不做「這個圈已經 N 天沒更新」這類提示。** 材料是真的，但那會變成一台機器在提醒你
   失去了什麼。設計討論裡聽起來深刻的東西，凌晨兩點看到會很難受。
   軟體把東西留住就夠了；什麼時候回頭看、看不看得下去，是人的事，不該由通知決定。

> 附帶：這個架構**已經**有「不需要任何人繼續存在也能存在」的性質——local-first、
> 刪除是墓碑而非抹除、匯出是完整 JSON、沒有帳號沒有伺服器。一個不再更新的圈，
> 同步過來的那份帳仍然完整、離線可讀。這不是要新增的功能，是既有工程決定的副產品，
> **改任何東西之前先確認沒有把它弄丟**。

## 五、如果真的要做圈層，技術前提先定死

**這些是動工前就該鎖定的，不是實作時再決定的。**

| 決定 | 理由 |
|---|---|
| `ExpenseRecord.ledgerId?: string`，**缺席即預設帳本** | 不要升級時補寫。補寫＝為每一列 `tickClock()` 換新信封，把一整批**意義不明的「編輯」**推到對方手機（同「不改寫既有分類名」的理由）。讀取時 `?? DEFAULT` 就好：零寫入、零同步風暴 |
| **`ledgerId` 不可變**（生在哪個圈就永遠在哪個圈） | ⚠️ **最重要的一條**。允許搬動的話會撞到 LWW 解不了的東西：某筆從家族帳移到個人帳，對「原本看得到、現在不該看到」的人需要的是**撤回**而不是刪除，而墓碑會把「刪掉了」傳播給所有人＝對方帳面憑空少一筆。定為出生時決定，這一整類問題消失，而且它也誠實——「這筆是家族旅遊的帳」本來就是記帳當下的判斷 |
| 只有 `records` 與 `budget` 帶 `ledgerId` | `Person` 全域（人就是人，不因圈而異）；`Category`／`MerchantRule` 全域（分類是你的語彙，每圈一套八分類會很痛苦）。順帶：`Budget` 從單例變成每圈一份是**改善**——家族旅遊本來就該有自己的預算 |
| DB v2 → v3 **只新增 `ledgers` store，不碰 records** | 升級護欄已修成 `oldVersion === 1` 才清空，所以這是安全的 |
| 同步 checkpoint 從 `peerDeviceId → HLC` 變成 `(peerDeviceId, ledgerId) → HLC` | **真正的工程重點在這裡**：它把「全有全無的信任邊界」變成**部分複製**，而那是現有架構最大的隱含前提。protocol.ts 是純 reducer + 事件泵測試，改動是加法不是重寫，但要重新想一遍收斂性 |
| 非預設圈的記錄，**雙方 hello 都宣告支援才送** | 混版本期間：舊版收到帶 `ledgerId` 的記錄不認得那個欄位，會當成一般記錄存起來並顯示在全家帳裡（`mergeRow` 只比信封，擋不住）＝**洩漏**。「雙方都要宣告」這條規則本身就是 feature flag（同 #11a 配對密鑰的手法） |

### 資料模型的岔路：已定案

原本這裡懸著一個「動工前必須先回答」的問題——**「家族帳」裡的一筆帳，是誰的帳？**
兩條路會長出完全不同的資料模型：

- **記帳者的**（他先墊了，家族欠他）⇒ 需要「應收／應付」
- **這個圈共同的**（大家都在花這筆）⇒ 只是換一個 `ledgerId`

**原則一把它關掉了。答案是後者：**

> 家族帳的一筆帳是**這個圈共同的**，實作上就只是換一個 `ledgerId`，
> **不引入應收／應付**。

理由：走「記帳者的」那條路，等於把家族帳變成家族**債本**。而債指向未來、會產生義務，
義務產生槓桿——那正是原則二要避開的脅迫來源。這個 app 從第一天就只標 `paidBy`
而不算誰欠誰，那條線在家族圈裡同樣不能跨。

真的有人先墊了錢，那是**圈外的事**（現實中就是在 LINE 上講一聲、下次換你請）。
這個 app 不承接那個語意——它記的是**花了什麼**，不是**誰欠誰**。

## 六、統一發票是唯一有外部背書的**記錄**

全 app 只有發票號碼有外部背書（財政部發的、唯一的）：記錄可以被**遺漏**，但無法被**捏造**。
這讓它在**對自己**的那面鏡子裡特別有用——它是唯一你騙不了自己的那部分。

但**別把它變成信號**（原則一）：

- 它有系統性偏誤——現金、小攤販、傳統市場全部不算，而那正是長輩的主要消費形態
- 更根本的是，「有背書的比例」一旦拿來看**別人**，就又回到把表態誤讀成證據

⇒ **可以當自己看的輔助資訊，絕不可當評分、更不可跨人比較。**
（任何評分都會變成脅迫的槓桿——原則二。）

  class（≥3 人才會走到，夫妻倆碰不到）。同類的還有 `.brush-text`、`.split-bar`，
  以及完全沒有消費者的 `FadeImg`（連帶 base.css 的 `.fade-img` 是死碼）。
  值得單獨一輪「className 字面量 vs 已定義選擇器」的清查，並補一條測試。

  要真的到 44 得把籤條加粗一倍、比例從 1:2.8 變 1:1.7，那就不是籤條了——這是刻意的取捨，
  記在這裡是為了下次有人量到時知道不是漏掉。
